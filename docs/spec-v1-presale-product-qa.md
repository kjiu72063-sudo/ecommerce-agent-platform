# V1 售前商品问答规格

> 状态：规格草案，可进入任务拆分
> 版本：v1.0-draft
> 更新时间：2026-09-07
> 依据：`CONTEXT.md`、`docs/product-purpose.md`、`docs/version-boundary.md`、`docs/domain-model.md`、`docs/domain-decisions.md`

## Problem Statement

电商平台内部的商品运营和客服运营人员在处理售前问题时，需要在商品资料、规格和规则中查找信息，再手工组织回复。现有流程存在以下问题：

- 商品资料分散，查找和核对成本高；
- 回复事实缺少明确来源，后续无法审查；
- 不确定或超出商品范围的问题容易被过度自信地回答；
- 无法追溯一次回答实际使用的知识、Agent 配置和运行过程；
- 自动化系统可能在尚未具备权限和审批边界时执行不应发生的业务写操作。

## Solution

提供一个面向内部商品运营/客服运营人员的只读售前问答辅助闭环：

```text
ProductQuestion
→ ProductScope
→ 已发布商品知识检索
→ 租户/权限过滤
→ 字段/片段级 EvidenceItem
→ ContextPackage
→ AnswerDraft
→ accepted / edited / escalated / discarded
→ Task / AgentRun / Event / provenance 追溯
```

V1 只生成供内部人员审核和处置的回答草稿，不代表已向消费者发送消息，也不执行任何商品、订单、库存、价格、支付或外部消息写操作。

## User Stories

1. 作为商品运营人员，我希望提交一个绑定明确商品的问题，以便系统不会在错误商品范围内检索资料。
2. 作为客服运营人员，我希望提交一个售前问题，以便快速得到可审核的回答建议。
3. 作为内部操作者，我希望请求带有租户和身份信息，以便系统执行正确的访问边界。
4. 作为内部操作者，我希望重复提交同一请求不会无限创建重复任务，以便避免重复运行和重复记录。
5. 作为内部操作者，我希望系统只使用商品运营团队维护并已发布的知识，以便回答基于经过审核的资料。
6. 作为内部操作者，我希望看到回答引用的具体字段或片段，以便核对事实来源。
7. 作为内部操作者，我希望看到知识来源的版本和定位，以便在资料更新后仍能解释历史回答。
8. 作为内部操作者，我希望不同租户的商品知识默认隔离，以便避免跨租户信息泄露。
9. 作为内部操作者，我希望超出商品范围的问题被识别出来，以便避免把其他商品资料误用于当前回答。
10. 作为内部操作者，我希望没有可靠证据时系统明确建议转人工，而不是编造答案。
11. 作为内部操作者，我希望证据冲突时系统明确提示冲突，以便由人工判断哪个资料有效。
12. 作为内部操作者，我希望涉及实时价格、库存或配送的问题转人工，以便避免使用过期的固定资料作出承诺。
13. 作为内部操作者，我希望权限校验失败时系统拒绝运行并说明原因，以便发现配置问题。
14. 作为内部操作者，我希望系统生成结构化回答草稿，以便统一查看答案、依据、置信度和人工建议。
15. 作为内部操作者，我希望回答草稿不把置信度信号伪装成准确率，以便正确理解系统的不确定性。
16. 作为内部操作者，我希望接受原始草稿，以便将其标记为内部采用结果。
17. 作为内部操作者，我希望编辑回答草稿，以便修正措辞或补充人工判断。
18. 作为内部操作者，我希望编辑后仍能看到原始草稿，以便保留完整审计链路。
19. 作为内部操作者，我希望编辑后的回答标记为 `edited`，以便区分原始接受和人工修改采用。
20. 作为内部操作者，我希望转人工时保存原因，以便人工接手者了解系统为什么没有完成回答。
21. 作为内部操作者，我希望丢弃不合适的回答草稿，以便明确该结果没有被采用。
22. 作为内部操作者，我希望 `accepted` 和 `edited` 不自动代表已发送给消费者，以便保留现有客服流程的发送控制权。
23. 作为运营管理人员，我希望通过 `run_ref` 追溯一次回答使用的输入、配置、证据和结果，以便进行质量复核。
24. 作为运营管理人员，我希望能够区分业务问题状态和技术运行状态，以便知道是回答未采用，还是系统执行失败。
25. 作为运营管理人员，我希望运行关键阶段都有事件记录，以便发现检索、上下文组装或回答生成在哪一步失败。
26. 作为运营管理人员，我希望运行记录固定保留 30 天，以便支持短期复盘同时避免无限保存。
27. 作为商品运营人员，我希望未来能够维护和审核已发布商品知识，以便知识来源保持业务可控。
28. 作为平台维护人员，我希望 Agent、Prompt、ContextPolicy 和 PermissionProfile 的实际版本被冻结在运行记录中，以便配置变化不会改写历史解释。
29. 作为平台维护人员，我希望 V1 工具只能执行只读知识查询，以便原型阶段没有隐藏业务副作用。
30. 作为平台维护人员，我希望检索、回答和处置失败都产生明确结果，以便测试能够发现首次偏离位置。
31. 作为测试人员，我希望固定商品资料集和固定问题集可以重复运行，以便比较不同实现的行为变化。
32. 作为测试人员，我希望契约不满足时运行明确失败，以便错误不会被转换为空回答。
33. 作为测试人员，我希望同一个问题的输入、证据和回答能关联到同一个 Task 和 AgentRun，以便验证链路完整性。
34. 作为测试人员，我希望只读边界有负向测试，以便确认系统没有执行改价、下单、库存写入或消息发送。
35. 作为系统维护人员，我希望未来可以将 JSON/内存知识替换为其他适配器，而不改变 ProductQuestion、EvidenceItem 和 AnswerDraft 的业务语义。

## Implementation Decisions

### 1. 业务边界

- V1 只支持内部商品运营/客服运营人员；消费者是间接受益者。
- 一次 `ProductQuestion` 必须绑定一个明确商品。
- V1 不支持多商品比较、商品集合和跨商品推荐。
- V1 的输出是 `AnswerDraft`，不是消费者最终消息。
- `accepted` 和 `edited` 表示内部采用，不表示已发送。

### 2. 业务对象

必须定义以下业务对象及其关联：

- `Tenant`；
- `Operator`；
- `Product`；
- `ProductScope`；
- `ProductQuestion`；
- `ProductKnowledgeSource`；
- `EvidenceItem`；
- `AnswerDraft`；
- `HumanDisposition`。

平台对象继续使用 B0–B3 已有对象：

- `AgentSpec`；
- `PromptPackage`；
- `ContextPolicy`；
- `PermissionProfile`；
- `Task`；
- `AgentRun`；
- `ContextPackage`；
- `ToolCall`；
- `Event`；
- `Artifact`。

### 3. 知识来源和检索

- 原型唯一知识来源是项目内版本化 JSON 商品资料集。
- 未来业务权威由商品运营团队维护和审核已发布知识。
- V1 使用确定性检索，不接入向量数据库或外部 RAG 平台。
- 检索必须返回候选与选择理由；被回答实际使用的内容必须转为 `EvidenceItem`。
- `EvidenceItem` 至少记录来源 ID、来源版本、字段/片段定位、内容摘要、租户和商品归属。
- 无结果、冲突或超出范围时不得生成无依据事实。

### 4. 输入契约

`ProductQuestion` 输入至少包含：

- `question_id`；
- `tenant_id`；
- `submitted_by`；
- 一个明确的 `product_ref`；
- `question_text`；
- 可选的已授权会话上下文；
- 请求时间；
- 长度至少为 8 的幂等键。

输入必须验证：

- 操作者属于当前租户；
- 商品属于当前租户；
- 商品范围不是空值；
- 问题不是空白；
- 请求未超出 V1 单商品范围；
- 同一幂等键的重复请求遵守既定幂等语义。

### 5. 输出契约

`AnswerDraft` 至少包含：

- `answer_id`；
- `question_ref`；
- `run_ref`；
- `answer_text`；
- `evidence_refs`；
- `confidence_signal`；
- `need_human`；
- `reason_codes`；
- 实际 Agent/Prompt/Policy/模型或替代实现版本引用；
- 生成时间。

回答成功的必要条件：

- 事实性内容有字段/片段级证据引用；
- 或明确标记 `need_human=true`，并给出原因；
- 不把模型自报分数称为准确率；
- 不包含未经证据支持的价格、库存或业务承诺。

### 6. 处置契约

`HumanDisposition` 支持：

- `accepted`：接受原始草稿；
- `edited`：保存编辑后草稿并标记为采用；
- `escalated`：转人工并保存原因；
- `discarded`：明确丢弃草稿。

编辑规则：

- 原始草稿不可被覆盖；
- 编辑后内容形成新的版本或关联 Artifact；
- 记录编辑人、编辑时间和处置原因；
- `edited` 不代表已发送给消费者。

### 7. ContextPackage 和运行关联

业务链路必须形成以下关联：

```text
ProductQuestion
→ Task
→ AgentRun
→ ContextPackage
→ AnswerDraft
→ HumanDisposition
```

`ContextPackage` 必须：

- 包含问题、Agent 配置、Prompt、证据和策略允许的上下文；
- 为每个来源保留 provenance；
- 记录内容摘要和总 token 数；
- 通过 B0 模型校验；
- 超预算时显式失败或转人工。

`AgentRun` 必须冻结实际使用的：

- `AgentSpec`；
- `PromptPackage`；
- `ContextPolicy`；
- `PermissionProfile`；
- 知识来源版本；
- 模型或模拟实现版本。

### 8. 状态映射

业务状态：

```text
submitted → scoped → processing → answered
answered → accepted | edited | escalated | discarded
submitted/scoped/processing → failed | cancelled
```

技术状态继续沿用 B0/B2：

```text
Task: created → validated → queued → running → succeeded / failed
AgentRun: created → resolving → ready → running → succeeded / failed
```

技术状态不得直接替代业务处置状态。一次运行失败不等于内部用户丢弃回答；回答被编辑也不等于技术运行失败。

### 9. 权限和只读边界

- 跨租户访问默认拒绝。
- 知识查询必须同时受租户、操作者和单商品范围约束。
- V1 只允许只读知识查询 ToolCall。
- 禁止改价、下单、库存写入、支付、订单操作、商品资料修改和外部消息发送。
- 权限失败必须产生明确失败事件和人工处置建议。
- 不在 V1 引入完整 RBAC/ABAC、通用多协议工具执行器或容器沙箱。

### 10. 失败和转人工

以下条件必须转人工或产生明确失败：

- 无证据；
- 证据冲突；
- 问题超出商品范围；
- 涉及实时价格、库存或配送；
- 权限拒绝；
- 知识来源不可用；
- Context 超预算；
- 模型或替代生成器失败；
- 契约校验失败。

不得：

- 静默吞掉错误；
- 用空列表伪装没有问题；
- 在无证据时生成确定事实；
- 通过提高置信度掩盖异常。

### 11. 保留和审计

- V1 原型运行记录固定保留 30 天。
- 保留 Task、AgentRun、ContextPackage 摘要、AnswerDraft 版本、EvidenceItem 引用、HumanDisposition 和关键 Event。
- Event 和 provenance 为追加型历史事实。
- 删除或到期处理不得修改已发生事实的语义。
- 记录必须支持通过 `run_ref` 追溯一次问答。

### 12. 测试接缝

主测试接缝是一个最高层的问答应用服务接缝：

```text
输入 ProductQuestion
→ 运行只读售前问答
→ 输出 AnswerDraft / HumanDisposition / trace refs
```

该接缝使用固定商品 JSON、确定性检索和模拟生成器，验证外部行为而不是内部类结构。

现有 B0–B3 测试继续作为支撑：

- B0 模型、Schema 和状态机一致性测试；
- B1 Registry、依赖、审计和 SQLite 测试；
- B2 Task/Run/Event/Checkpoint 测试；
- B3 Context 预算、去重、排序和 provenance 测试。

## Testing Decisions

### 测试原则

- 优先测试外部业务行为，不测试未承诺的内部实现细节；
- 固定输入应得到确定性可比较结果；
- 每个失败出口都必须有可断言的错误或人工处置结果；
- 正向测试不能单独证明安全边界，必须有负向测试验证无写操作；
- 业务状态和技术状态分别断言；
- 任何回答成功断言都必须同时检查证据或 `need_human`。

### 必须覆盖的端到端场景

1. **有证据的正常问答**：绑定单商品，检索到字段/片段证据，生成带引用的 AnswerDraft。
2. **无证据转人工**：问题无法从商品资料中找到依据，输出 `need_human=true`。
3. **证据冲突转人工**：多个已发布来源对同一事实冲突，不生成确定答案。
4. **超商品范围**：问题涉及其他商品或未绑定商品，拒绝跨范围检索并转人工。
5. **实时信息转人工**：问题涉及价格、库存或配送，V1 不接入实时系统，必须转人工。
6. **跨租户拒绝**：问题租户与商品知识租户不一致，权限拒绝且记录事件。
7. **Context 超预算**：证据集合超预算，明确失败或转人工，不静默截断。
8. **草稿接受**：原始草稿进入 `accepted`，且不产生发送消费者消息的副作用。
9. **草稿编辑**：原始草稿保持不变，生成编辑后版本并进入 `edited`。
10. **转人工**：记录人工处置原因和运行引用。
11. **丢弃草稿**：明确记录 `discarded`，不篡改原始运行事实。
12. **运行追溯**：通过 `run_ref` 找到问题、配置、Context、证据、回答和关键事件。
13. **幂等提交**：同一幂等键重复提交不创建不受控的重复业务任务。
14. **只读负向测试**：证明流程不会调用改价、下单、库存、支付、订单或外部发送能力。
15. **运行失败**：模拟知识源或生成器失败，产生显式失败状态和人工建议。

### 既有测试资产

实现时优先复用当前根级测试入口：

```bash
uv run pytest -q
```

现有 B0–B3 测试是回归基础；V1 新增测试应放在根级规范测试目录中，并通过最高层应用服务接缝验证主路径。

## Out of Scope

本规格不包含：

- 面向消费者的生产聊天入口；
- 售后、退款、投诉和订单处理；
- 自动下单、改价、优惠、库存写入和支付；
- 真实价格、库存、配送查询；
- 真实生产 RAG、向量数据库和多模态素材；
- 直播切片 Agent；
- 自媒体运营 Agent；
- 多 Agent 协作；
- 完整 B4 Harness；
- 完整 RBAC/ABAC 权限平台；
- 通用 MCP/HTTP/gRPC 工具执行器；
- 容器沙箱；
- B5 复杂 Loop、自动规划、无限重试和自主反思；
- PostgreSQL、消息队列、对象存储生产部署；
- 分布式事务、高可用、灾备和跨区域恢复；
- 消费者消息发送和外部客服系统写入；
- 生产合规认证和正式 SLA。

## Further Notes

### 实现前仍需量化的规则

这些事项不再阻塞产品方向，但必须在 ticket 验收标准中量化：

- 字段/片段定位的具体格式；
- 确定性检索的关键词、同义词、排序和阈值；
- 证据冲突的判定规则；
- 置信度信号的计算公式和展示范围；
- AnswerDraft 的输出字段和版本号格式；
- `escalated` 是否关联外部人工工单 ID；
- `edited` 版本的差异记录格式；
- 30 天保留从创建、完成还是最后访问时间起算；
- 商品知识“已发布”的最小状态；
- JSON 资料集的商品、租户、版本和字段格式；
- 模拟生成器与真实模型之间的替换验收标准。

### 进入实现的顺序

1. 先定义 V1 业务对象和输入/输出契约；
2. 再定义确定性知识检索和 EvidenceItem 规则；
3. 再打通 ProductQuestion → AnswerDraft 的端到端原型；
4. 再加入 HumanDisposition 及版本留痕；
5. 通过验收后再评估 B4 最小执行边界；
6. 不因平台已有 B0 字段而自动扩展业务范围。

### 当前门禁结论

规格可以进入 `/to-tickets`。

但进入任务拆分时，必须优先拆出一条可独立验证的 tracer bullet：

```text
固定商品资料
→ 单商品 ProductQuestion
→ 确定性 EvidenceItem
→ ContextPackage
→ AnswerDraft
→ accepted / edited / escalated / discarded
→ Task / AgentRun / Event 追溯
```
