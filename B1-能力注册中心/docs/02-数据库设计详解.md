# B1 数据库设计详解

> 文件位置：`B1-能力注册中心/docs/01-数据库设计.sql`
> 数据库：PostgreSQL 15+

---

## 一、表结构总览

```
definition_objects          # 定义对象主表（核心）
definition_versions         # 版本历史表（审计）
definition_dependencies     # 依赖关系表（解析）
audit_log                   # 审计日志表（安全）
```

## 二、definition_objects（定义对象主表）

### 2.1 作用

存储所有 8 种定义对象的核心数据。

### 2.2 字段设计

#### id（主键）

```sql
id VARCHAR(64) PRIMARY KEY
-- 如 agt_0198f6d0-7ef0-7b0e-a0d3-5f9c96c7f411
```

**为什么用 VARCHAR 而不是 UUID？**
- ID 包含类型前缀（`agt_`、`skl_` 等）
- 前缀是业务语义的一部分
- PostgreSQL 的 UUID 类型不能存储前缀

#### kind（资源类型）

```sql
kind VARCHAR(32) NOT NULL
-- 如 AgentSpec, SkillManifest
```

**8 种定义对象**：
- AgentSpec、SkillManifest、ToolManifest、PromptPackage
- ModelPolicy、ContextPolicy、LoopProfile、PermissionProfile

#### key + namespace + version（逻辑唯一键）

```sql
key VARCHAR(128) NOT NULL        -- 如 programming-agent
namespace VARCHAR(128) NOT NULL  -- 如 ecommerce
version VARCHAR(32) NOT NULL     -- 如 1.0.0
UNIQUE(namespace, key, version)
```

**为什么这样设计？**
- 同一技能可以有多个版本（1.0.0、1.1.0、2.0.0）
- 不同命名空间可以有同名技能
- 防止重复注册

#### spec（核心规格）

```sql
spec JSONB NOT NULL
```

**为什么用 JSONB？**
- 不同 kind 的 spec 结构不同
- JSONB 提供灵活性
- PostgreSQL 的 JSONB 支持索引和查询
- Pydantic 模型负责结构验证

#### status（状态信息）

```sql
status JSONB NOT NULL
-- 如 {"phase": "active", "observed_revision": 1, "activated_at": "..."}
```

**为什么用 JSONB？**
- 状态字段较少，不需要独立列
- 便于查询 `status->>'phase'`

#### content_digest（内容摘要）

```sql
content_digest VARCHAR(70) NOT NULL
-- 如 sha256:a1b2c3d4...
```

**作用**：
- 验证 spec 完整性
- 检测内容变更
- 缓存键

### 2.3 索引设计

| 索引 | 作用 | 查询场景 |
|---|---|---|
| `idx_definition_kind` | 按类型查询 | 查询所有 AgentSpec |
| `idx_definition_namespace_key` | 按命名空间和 key 查询 | 最常用查询 |
| `idx_definition_phase` | 按阶段查询 | 查询所有 active 对象 |
| `idx_definition_tenant` | 按租户查询 | 多租户隔离 |
| `idx_definition_labels` | 按标签查询 | JSONB GIN 索引 |
| `idx_definition_kind_phase` | 按类型和阶段查询 | 查询 active 的 AgentSpec |

## 三、definition_versions（版本历史表）

### 3.1 作用

记录每次版本变更，用于审计和回溯。

### 3.2 为什么需要？

- **审计**：追踪谁在什么时候修改了什么
- **回溯**：可以查看任意历史版本
- **摘要校验**：验证 spec_snapshot 的 content_digest

### 3.3 设计要点

- `spec_snapshot` 是不可变的快照
- 每次版本变更都记录
- 不删除历史记录

---

## 四、definition_dependencies（依赖关系表）

### 4.1 作用

记录定义对象之间的依赖关系。

### 4.2 为什么需要？

- **依赖解析**：AgentSpec 启动时需要解析所有依赖
- **循环检测**：防止 A 依赖 B，B 依赖 A
- **影响分析**：修改一个对象时，知道哪些对象受影响

### 4.3 依赖类型

| 类型 | 说明 | 示例 |
|---|---|---|
| `prompt` | Prompt 依赖 | AgentSpec → PromptPackage |
| `context` | Context 策略依赖 | AgentSpec → ContextPolicy |
| `model` | 模型策略依赖 | AgentSpec → ModelPolicy |
| `loop` | Loop 配置依赖 | AgentSpec → LoopProfile |
| `permission` | 权限配置依赖 | AgentSpec → PermissionProfile |
| `skill` | 技能依赖 | SkillManifest → SkillManifest |
| `tool` | 工具依赖 | SkillManifest → ToolManifest |

## 五、audit_log（审计日志表）

### 5.1 作用

记录所有操作，用于安全审计。

### 5.2 记录内容

- 操作时间
- 操作类型（create/update/transition/delete）
- 资源 ID 和类型
- 操作者信息
- 变更前后状态

## 六、关键设计决策

### 1. JSONB vs 独立列

| 选择 | 适用场景 |
|---|---|
| JSONB | 结构灵活、字段较多、不同 kind 结构不同 |
| 独立列 | 频繁查询、需要索引、字段固定 |

**spec 用 JSONB**：不同 kind 结构不同
**kind 用独立列**：频繁查询和过滤

### 2. 逻辑唯一键

```sql
UNIQUE(namespace, key, version)
```

**好处**：
- 支持多版本共存
- 防止重复注册
- 按 key 查询最新版本

### 3. 索引策略

- JSONB 字段用 GIN 索引
- 常用查询字段用 B-tree 索引
- 组合查询用组合索引
